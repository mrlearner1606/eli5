The model that shows its work gets the answer right.

That's the whole idea behind Chain of Thought and ReAct — two names for one promise: think in steps before you speak.

ThoughtThe customer asked for the cheapest flight. I should first look up available flights.
ActionCall the tool search_flights("BLR → DEL")
ObserveTool returned 3 flights: ₹4,200 · ₹5,900 · ₹7,100
Thought₹4,200 is the cheapest. I have enough to answer now.
Final“The cheapest is the 6:10 AM flight at ₹4,200.”

↑ A real reasoning trace. Thought → Action → Observation → repeat → Answer.

01

Why this exists: the model was blurting

A language model predicts the next word. If you ask a hard question and it must answer immediately, it has only one shot — and it often guesses.

✗ Zero-shot (blurts)
“Q: A shop had 23 apples, sold 9, got 12 more. How many?

A: 30”
✓ Chain of Thought (shows work)
“Q: A shop had 23 apples…

Let me work through it. 23 − 9 = 14. Then 14 + 12 = 26. So the answer is 26.”

🧸 The kid version

Think of a maths test. One kid writes the answer straight away and gets it wrong. The other kid writes the steps down — and by writing them, each small step becomes easy.

The model is exactly the same. Every token it writes becomes context for the next token. So if it writes “let me add these first…”, that written-out thought is now something it can build on, instead of having to hold everything in its head.

💡 In one breath: Chain of Thought turns one giant leap into a staircase of small, checkable steps. That is why accuracy on reasoning tasks goes up.
02

Chain of Thought: prompt it, don't train it

CoT is a prompting technique, not a model you fine-tune. You don't change the weights — you change what you ask for.

Two ways to switch it on

1. Zero-shot CoT — just add one magic line to your prompt:

Let's think step by step.

2. Few-shot CoT — show 1–3 worked examples where the reasoning is written out, then give the real question. The model copies the shape of your example.

💡 In one breath: zero-shot CoT is one sentence added to your prompt. Few-shot CoT is a handful of worked examples. Neither requires training.

⚠️ The part developers forget

The chain is working memory, not user-facing output. If you return the raw reasoning to your app, you're paying tokens, leaking how your system works, and exposing the model's wrong turns.

Pattern: ask the model to reason inside a clearly-marked block, then ask it to output only the final answer (or parse just the answer field). Bedrock gives you structures for this — a well-defined output schema, or a separate final-answer turn.

03

ReAct: Chain of Thought that can use tools

Plain CoT is smart but trapped inside its own head. It can't check the weather, query a database, or read your ticket system. ReAct = Reasoning + Acting. It lets the model think, do something, look at what happened, and think again.

Thoughtreason about it
Actioncall a tool
Observationsee the result
ThoughtThe model writes its reasoning — what it knows, what's missing, and which tool would help.
ActionIt emits a tool call in a fixed format: e.g. search_orders({"id":"A19"}).
ObservationYour code runs the tool and feeds the result straight back into the model's context.

🧸 Kid version

CoT is a kid thinking out loud. ReAct is that same kid allowed to open the book, check the map, or ask the teacher, then carry on thinking with the new fact in hand — and repeat until the answer is solid.

The critical bit: the model never runs your code. It only asks. Your orchestration layer executes the tool and pastes the output back in. That boundary is where security lives.

💡 In one breath: ReAct = CoT + a tool belt + a loop, and you (not the model) hold the belt.
04

Side by side

TechniqueThinks in steps?Can use tools?Typical costBest for
Plain prompt No No Lowest Simple FAQs, summarising, rewriting, classification
Chain of Thought Yes No More output tokens Maths, logic, planning, multi-step reasoning where the answer must be right
ReAct Yes Yes Highest — many model round-trips Tasks needing live data or side effects: book it, look it up, update the record

Rule of thumb: don't reach for ReAct when CoT will do. Every loop adds latency and cost. Start simple; add tools only when the model genuinely needs outside facts.

05

Where this lives on AWS

You rarely build the loop from scratch. AWS gives you the runtimes, and the reasoning pattern still describes what happens inside them.

🤖 Amazon Bedrock Agents

The managed ReAct engine. You define an action group (an OpenAPI schema or a Lambda function) and a knowledge base. The agent builds the Thought → Action → Observation loop for you, calls your Lambda, and returns the final answer with a trace you can inspect.

🔗 Bedrock Knowledge Bases

Your retrieval tool. Instead of forcing the model to remember facts, the agent searches your documents and feeds the closest passages back — the Observation step, with embeddings doing the finding.

🧱 Bedrock Converse API

The plain building blocks. You own the loop: send messages, receive a tool-use request, run the tool yourself, append the result as a toolResult, and send again. Best when you need custom orchestration.

🛡️ Bedrock Guardrails

Your boundary layer. Grounding checks, denied topics, PII redaction, and a contextual grounding score that flags when an answer isn't supported by the retrieved source — crucial when a reasoning chain drifts.

🚀 Amazon Bedrock AgentCore

Runtime and tooling for longer-running, production agents: sessions, memory, identity, and isolated execution so your action tools run safely outside the model.

🧪 Amazon SageMaker

When you want to go deeper: evaluate reasoning quality with your own harness, fine-tune a model to reason in your domain style, or host an open-weights reasoning model on your own endpoints.

🔁 AWS Step Functions

Deterministic orchestration around the model. Encode the multi-step workflow, retries, and human-approval gates as a state machine so a flaky tool call can't derail the whole task.

📊 Amazon CloudWatch & model invocation logging

Log the full trace: prompt, thoughts, tool calls, observations, and final answer. This is how you debug a bad chain and how you prove, later, why the model said what it said.

A reference architecture (say it in an interview like this)

Entry: API Gateway → Lambda → Amazon Bedrock Agent. Reasoning: the agent runs a ReAct loop on a chosen foundation model. Tools: action-group Lambdas call your systems; a knowledge base supplies grounded context. Guardrails: Bedrock Guardrails filter and grounding-check the output. Identity: AgentCore keeps per-user sessions isolated. Observability: CloudWatch + invocation logging capture the full trace. Approval: Step Functions gates any irreversible action.

06

Certification & job relevance

Prompting techniques sit squarely in the AWS Gen AI certification objectives — and they're a standard interview screen for Gen AI developer roles.

What to be able to say out loud

AWS Certified AI Practitioner (AIF-C01) — foundational prompt-engineering domain: you should know what chain-of-thought prompting is, why it improves reasoning output, and that ReAct combines reasoning with tool use.

AWS Certified Machine Learning Engineer – Associate (MLA-C01) — the applied Gen AI domain expects you to pick the right orchestration approach for a task, define Bedrock agents with action groups, and evaluate/guardrail the output.

Interview favourite: “When would you use ReAct over plain CoT?” A strong answer names the cost/latency trade-off, the need for live or private data, the risk of runaway loops, and how you'd bound iterations and gate risky actions.

💡 Sound like a pro: talk about the trace, not just the answer. In production Gen AI, the ability to inspect and evaluate the reasoning path is the skill that's actually paid for.
07

Gotchas & fine print

⏱️

Latency and cost compound. A ReAct task with 8 loop iterations is 8+ model round-trips. Cap iterations, cache tool results, and route easy requests to plain prompts.

🌀

Loops can spin. Without a hard stop the agent may retry a failing tool forever. Always set a max-iteration ceiling and a fallback message.

🔒

The model never executes anything. It only requests. Your orchestrator runs the tool — so validate arguments, scope IAM permissions tightly, and never expose an action you wouldn't let a stranger call.

🎭

A confident chain isn't a correct chain. The model can reason beautifully to the wrong place. Ground answers in retrieved sources and use grounding/faithfulness checks rather than trusting the prose.

🙈

Don't leak the chain. Raw reasoning can expose system instructions and confuse end users. Return the answer, log the trace internally.

🧩

Tools are harder than prompts. Most project failures are vague tool descriptions and bad schemas, not bad models. Be precise about what each tool does and when to use it.

  3. 03ReAct = Reasoning + Acting — CoT plus tool calls plus a loop, until the model has enough to answer.
  4. 04Your code runs the tools, never the model. That boundary is your security perimeter.
  5. 05On AWS, Bedrock Agents is managed ReAct; Converse API is DIY ReAct; Knowledge Bases is the retrieval tool; Guardrails is the safety net.
