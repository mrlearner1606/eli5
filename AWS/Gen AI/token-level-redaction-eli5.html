Token-level redaction, explained simply

Picture handing your homework to a stranger — but first you scribble over every address, phone number and password. Then you tear the page into little strips and hand those over instead. Token-level redaction is that scribbling, done before the paper is ever torn up.

Why this exists

Models don’t read words — they read tokens

A foundation model never sees your sentence as a sentence. Text is chopped into tokens first: short chunks of characters, usually a word, part of a long word, a number, or a piece of punctuation. Everything the model has ever processed lived in a token at some point.

That matters because if a name, account number, or credential is sitting inside those tokens, the model can echo it back, summarize it into a response, pass it to a tool, or leave it in a request log. A careless prompt is a data-export channel you didn’t intend to open.

So the safest place to remove sensitive text is before it becomes tokens the model can see. Redaction that happens at that granularity — find the sensitive span, replace it, then let the text continue on its way — is what people mean by token-level redaction.

The one-line version: same idea as a bouncer checking IDs at the door, not inside the club. Sensitive values get swapped out at the boundary, so the model works with {NAME} instead of the actual person’s name.

The tricky part

Sensitive spans don’t line up with token boundaries

You might hope you can just “delete the token for the name.” You can’t. Tokenizers split text by frequency, not by meaning — an email address can land as one token, four tokens, or four-and-a-half.

one plausible tokenization of an email + card number

alice@example.com · card4111-1111-1111-1111

The sensitive value is smeared across several tokens, and where the seams land depends on the tokenizer — which can differ between model families. So redaction works on detected spans, not on token indexes.

The two halves of the job

  • Detect the span. ML-based PII detection reads context (“is this 41 an age or a house number?”), while pattern matching handles fixed shapes like an email or a booking ID.
  • Replace the span. The span is swapped for a placeholder — itself just another token — like {NAME} or [EMAIL-1].

What you do with the original value splits redaction into two flavours: one-way you throw it away, and reversible you keep a private mapping so you can put the real values back after the model answers.

The analogy

The mailroom with a black marker

Imagine a mailroom that forwards letters to a contractor who does the actual work. Three jobs, in order:

1Read the letter and spot the private bitsNames, addresses, card numbers, passwords, access keys — anything that identifies a person or unlocks an account.
2Black it out solidlyNot a thin line you can read through. The contractor should see {NAME}, not a blurry guess.
3Decide whether to keep the keyIf you keep a locked list of “what was under each black mark,” you can restore the real values in the reply. If you don’t, the data is gone for good — the simpler, safer default.
4Check your own workA second reader scans the outgoing pile to confirm nothing sensitive slipped past the marker.

That fourth step is the one teams skip and later regret. Redaction is a filter, and filters leak — so production setups verify the output rather than trusting the first pass.

The AWS toolkit

What an AWS Gen AI developer actually wires up

There isn’t one service called “token-level redaction.” You assemble it from a few pieces, and where you place the redaction step depends on whether the risky text is a live prompt, a stored document, or a model response.

🛡️

Amazon Bedrock Guardrails boundary

Sensitive information filters detect PII in input prompts and in model responses, then either block the whole thing or mask the values. Built-in PII types cover general (name, email, phone, address), finance (card number, IBAN, PIN), IT (IP, URL, AWS access key, AWS secret key), and several country-specific groups, and you can add your own regex for patterns the ML model doesn’t know, like an employee or booking ID.

🔎

Amazon Comprehend pre-model

DetectPiiEntities returns PII spans plus confidence scores; PII redaction jobs write out documents with the sensitive values replaced by placeholder tokens. This is the tool you reach for when you want the redacted text to exist before it is ever stored or embedded.

🧯

Amazon Macie verify

The second pair of eyes. A common pattern is to redact, then scan the output with Macie, quarantine anything still holding sensitive data, and only ingest the objects that passed.

🖼️

Bedrock Data Automation multimodal

Text is only half the problem. When documents, images, audio, or video carry PII, Bedrock Data Automation extracts and processes that content, and can be paired with Guardrails to detect and redact sensitive information across text and images.

🎫

ApplyGuardrail anywhere

Standalone evaluation lets you run the same guardrail against text that isn’t a live model call — for example a document on its way into a knowledge base. One policy, several checkpoints.

📦

Lambda + a mapping vault glue

The sample-code favourite: a function detects spans, replaces them with placeholders, keeps the mapping in a separate store, and restores real values in the final answer. Below the Foundation model, this is where token-level redaction usually lives.

Patterns that combine these pieces are well documented in AWS’s own guidance for protecting sensitive data in RAG applications, and in the Guardrails documentation for sensitive information filters.

The streaming trap

You can’t un-send a token

Buffered redaction is easy to reason about: collect the whole answer, inspect it, then show it. Streaming breaks that, because tokens leave the model — and reach your user — while the sentence is still being written. If a card number is already painted on the user’s screen, redacting it a moment later hasn’t helped anyone.

✗ Risky

Forward each chunk the instant it arrives, then try to catch sensitive content on the fly.

Feels instant. But a name can straddle two chunks, and a value already delivered can’t be recalled.

✓ Safer

Hold chunks until a unit of text has been evaluated, then release it.

Adds a little delay before the first visible token. That delay is the price of not leaking.

Guardrails documents configurable streaming behaviour for filtering content, and the practical guidance in AWS’s material outside the docs is that streaming output is evaluated continuously as it is produced. Exactly how much gets buffered, and what your SDK exposes, is worth checking in the current documentation before you pick a mode — this area moves.

Fine print

Gotchas that bite in production

  • Guardrails sensitive information filters evaluate text only — and tool use is a gap. PII the model writes into tool-call arguments, PII in tool results your app sends back, and PII in the tool definitions themselves are not covered by the filter. If your agent hands a customer email to a tool that writes a file, that email was never masked. Redact inside your application too.
  • Mask gives you a type, not a value. You get {NAME}, not the name. If your UI needs to show the real value afterwards, that placeholder doesn’t help — you need your own mapping vault, and now that vault is another thing to secure.
  • Detection is probabilistic, and regex is brittle. Guardrails describes its PII model as ML-based and context-dependent, supplemented by custom regex. Layer them: the ML side catches context, the regex side catches your boring-but-critical internal formats.
  • Overlapping spans. Sort your detections and resolve overlaps before you rebuild the string. Otherwise you get nested placeholders and offsets that no longer line up with the original text.
  • Redact on the way in and on the way out. A model can echo an input value or generate a plausible-looking one. Checking only the prompt protects only half the conversation.
  • Your logs are the leak you forgot about. Raw prompts, full model invocations, and error traces land in CloudWatch and crash reports. If you redact on the wire but log the original, you haven’t redacted anything.
  • Redaction is not authorization. Removing everything is the simplest policy, but when some users legitimately need to see a value (a doctor, a fraud analyst), redaction is the wrong tool — retrieve by role instead, and protect that path just as carefully.
  • Verify instead of assuming. Whatever you redact, add a check on the other side — scanning stored objects, sampling outputs, or reviewing the guardrail traces. One pass is a filter, not a guarantee.
TL;DR

The whole thing in a handful of lines

  • Token-level redaction means swapping sensitive spans for placeholders at the model boundary, before that text is ever processed as tokens.
  • Sensitive values straddle token boundaries, so you redact detected spans, not specific token indexes.
  • Guardrails sensitive information filters are the managed option: block the request/response, or mask the value with its type, like {NAME}.
  • Comprehend redacts before ingestion; Macie verifies the result; Bedrock Data Automation extends the problem to images and media.
  • Guardrails text filters don’t cover tool-use arguments, tool results, or tool schemas — handle those in your own code.
  • Streaming means tokens you’ve already sent can’t be recalled: buffer and evaluate, or accept the risk knowingly.
  • Redact inputs, outputs, and logs. Then verify — one pass is a filter, not a promise.

Say it in one breath: find the private bits 🧐 → cross them out before the model tokenizes them ✏️ → decide whether you kept a key 🔑 → check the result on the way out ✅ → and keep the raw values out of your logs 🧹.
