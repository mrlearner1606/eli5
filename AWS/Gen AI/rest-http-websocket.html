REST vs Streaming vs WebSocket

Every Gen AI app is just your app talking to a model. How it talks — one question, one parcel back, or an open phone line — decides how fast your AI feels. Explained like you're five, with a restaurant.

Step 0

Why does Gen AI care how we talk?

A classic API call is like a vending machine: press a button, get the whole snack instantly. But an LLM is not a vending machine — it writes its answer word by word, which can take seconds to minutes. So the plumbing question becomes real: do we wait for the whole essay, or start reading it as it's being written? And if your app is a voice agent, you need to talk and listen at the same time. Three transports, three personalities:

1

HTTP/REST — one question, one complete answer

Your app sends a request ("summarize this ticket"), waits, and receives the finished response in one piece. Simple, universal, easy to cache and debug.

2

Streaming (SSE over HTTP) — answer arrives word by word

Same request shape, but the response trickles in as chunks (server-sent events) the moment each token is generated. This is why ChatGPT-style interfaces feel fast.

3

WebSocket — an open two-way line

The connection stays open. Both sides send messages whenever they want — essential for live voice agents, multiplayer sessions, and anything genuinely real-time.

The ELI5 story

A restaurant with three kinds of service

Your AI app is the hungry customer. The model is the kitchen.

🍽️

REST/HTTP = à la carte

Order one dish. Wait. Get the whole plate.

You ask for the full answer and receive the full answer. Perfect when the task is one-shot and complete: classify this email, extract these fields, embed this chunk. Nobody expects the plate to arrive one noodle at a time.

AWS: Bedrock InvokeModel (plain HTTP POST → full JSON)
🍜

Streaming = chef's counter

Same order — but pieces arrive as they're ready.

The kitchen starts plating the moment the first noodle is done. You're reading the answer while it's being written. Total cooking time is identical — it just feels dramatically faster because you start consuming immediately.

AWS: Bedrock ConverseStream / InvokeModelWithResponseStream (chunked events)
📞

WebSocket = table phone to the kitchen

An open line — both sides talk whenever, for the whole meal.

You don't re-flag the waiter for every request; the line is just open. Send a new instruction mid-meal, get interrupts and updates pushed to you. That's live voice agents: speaking and listening simultaneously.

AWS: API Gateway WebSocket APIs + Lambda → Bedrock · AppSync subscriptions · Nova Sonic
Under the hood

What the wire actually looks like

Same Gen AI work, three shapes of conversation.

🍽️ REST — request → think → whole response

Your appHTTP POST + prompt → Bedrockgenerates everything → Your app200 OK · full JSON

One round trip, one payload. Dead simple to test with curl. The user stares at a spinner until it's done.

🍜 Streaming — request → think → many small chunks

Your appHTTP POST + prompt → Bedrockstreams token chunks… → Your appchunk · chunk · chunk ✅

Still HTTP — but the connection stays open while the server sends server-sent events (SSE). Render each chunk on arrival and the app feels instant.

📞 WebSocket — handshake → open line → both directions

Connectupgrade → connectionId ⇄ API Gateway WSroutes messages ⇄ Lambda + Bedrockreplies & pushes

The first handshake upgrades HTTP to a WebSocket. After that, either side sends JSON frames anytime until someone hangs up ($disconnect).

Fine print

Gotchas worth knowing

⚠️ The timeout trap

API Gateway integrations historically cap out around 29 seconds (higher limits are now configurable on some REST APIs). A slow 60-second generation can get decapitated mid-thought — stream it or use a WebSocket instead.

⚠️ WebSockets are stateful work

The connectionId is ephemeral. You store it (DynamoDB is the classic), route replies back through it, and handle $disconnect like a pro. More moving parts than a plain POST.

⚠️ Idle lines cost money

WebSocket connections bill for connection minutes even when nobody talks. REST charges only per request. If traffic is one-shot and sporadic, the open line is paying rent for nothing.

✅ Streaming is just HTTP

Same ports, same proxies, same auth patterns as normal REST — so it usually sails through corporate networks. WebSockets occasionally meet strict proxies that block the upgrade.

✅ First token beats total time

Users judge AI by how fast it starts answering. Streaming doesn't make the model faster — it makes waiting disappear. Optimize time-to-first-token.

✅ Match the voice pipeline

Real speech agents are bidirectional: microphone audio upstream, model audio downstream, simultaneously. That's WebSocket (or WebRTC) territory — e.g. Amazon Transcribe streaming and Nova Sonic.

TL;DR

Explain it to me in four lines

  • REST/HTTP = order a dish, get the whole plate: one-shot tasks like classification, extraction, embeddings (Bedrock InvokeModel).
  • Streaming = chef's counter: same request, tokens arrive as they're written — this is what makes chat feel alive (ConverseStream).
  • WebSocket = open phone line to the kitchen: live voice agents and sessions where both sides talk freely (API Gateway WebSocket APIs, AppSync, Nova Sonic).
  • Rule of thumb: one-shot → REST · generated text → streaming · live/voice → WebSocket. And when in doubt for text: stream it — users feel the difference instantly.
