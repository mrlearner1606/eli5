The idea

A brilliant brain, locked in an empty room.

A large language model has read the whole internet — but it is stuck in a room with no windows. It can't see your files, your database, or your company's APIs. It only knows what you hand it.

The old fix was to build a custom wire for every single thing you wanted to connect: one for your database, one for Slack, one for GitHub, one per model. Lots of glue code. Lots of upkeep.

MCP (Model Context Protocol) replaces all those custom wires with one standard plug. Describe your tool once as an MCP server, and any AI app that speaks MCP can use it — no new glue code.

🧸 In one breath: MCP is the USB-C of AI. One plug shape, and every tool in the room just works.

Why it exists

The "too many wires" problem (M × N)

Imagine 5 AI apps and 5 tools. If every app needed its own custom wire to every tool, that's 5 × 5 = 25 wires to build and keep alive. Add one tool and you rewire everything.

With MCP it's 5 + 5 = 10: five clients, five servers. Each side speaks one shared language, so anything can talk to anything. That's why MCP is often compared to LSP, the protocol that let every code editor talk to every language the same way.

How it works

Two parts: a client and a server

01 MCP client — the AI app: an agent on Amazon Bedrock, a coding assistant, or a chat app like Claude Desktop.
02 MCP server — a small program someone wrote that exposes one tool or data source in the standard way.
03 They connect — the client asks "what can you do?", the server lists its abilities, and the model calls them when needed.
04 Runs anywhere — servers can live on your laptop while you test, or run as hosted services across your AWS infrastructure.

Every server can offer three kinds of things:

🛠️ToolsActions the model can call — "look up this order", "send this message".
📄ResourcesData placed into the model's context — a file, a database row, an image.
📝PromptsReusable templates that show the model how to use a tool well.

On AWS

Where you use MCP as an AWS Gen AI developer

🧰 AWS MCP Servers (awslabs/mcp)

An open-source suite of ready-made MCP servers from AWS — for official docs, cost, diagrams, databases, and more — so your coding assistant already knows AWS best practices.

🤖 Amazon Bedrock AgentCore

AgentCore Gateway turns your APIs and Lambdas into MCP tools agents can discover and call, and AgentCore Runtime hosts agents that speak MCP in production.

🧵 Strands Agents SDK

AWS's open-source agent SDK with MCP support built in — point an agent at an MCP server and its tools show up automatically.

🗣️ Amazon Q & coding assistants

Coding assistants and chat apps act as MCP clients — connect an MCP server and they gain your tools inside the editor or chat.

🧸 Plain talk: on AWS you usually don't invent the protocol — you plug a ready-made AWS MCP server into your assistant, or wrap your own API as an MCP tool behind AgentCore Gateway.

Fine print

Gotchas worth knowing

  • ⚠️ It's a standard, not a service. MCP won't run anything for you — someone still has to host each server, locally or in the cloud.
  • 🔐 Servers are trust boundaries. A server can read data and take actions. Grant least-privilege credentials, review third-party servers, and never hardcode secrets.
  • 🔀 Local vs remote matters. Local (on your machine) is easiest for testing; remote servers need real authentication and network hardening.
  • 🚚 Transports have changed. Early setups leaned on SSE; newer guidance favors streamable HTTP. Check the current MCP spec before building.
  • ⏳ The ecosystem moves fast. AWS has been folding its labs MCP servers into a broader "Agent Toolkit for AWS", so names and recommended paths can shift — verify against current docs.
  • 🧠 Not magic memory. The model only gains what the connected servers expose — connect the right server, or it stays in the empty room.
