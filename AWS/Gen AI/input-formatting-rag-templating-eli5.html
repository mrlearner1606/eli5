Input formatting: the script the actor reads

A user types one casual question. Your backend has to turn it into a precisely formatted request that a model can read, with the right facts stapled in. Get the format wrong and you get errors, or worse, confident nonsense.

🧾Parse answer

🎬The Kollywood analogy

Think of a Tamil film shoot. The lead actor is brilliant, but they only perform the lines printed on the page in front of them. They cannot read the director's mind.

So the assistant director (your Lambda) prepares the scene page. They take the fixed script template with blank spaces, pull the right research notes (the retrieved chunks) from the file room, drop them into the blanks along with the question, and hand the actor one clean page. Same format every scene, different notes and questions each time.

🧠 The model is the actor. Your formatter is the assistant director. The prompt is the page the actor reads, and format is just the layout of that page.

🔀Two ways to hand the page over

Bedrock gives you two main doors. Both reach the same models, but the paperwork differs.

InvokeModel
🧾 The model's native form

You write the JSON in the exact shape that model family expects. Each provider has its own body:

  • Anthropic Claude: messages, anthropic_version, max_tokens
  • Meta Llama: prompt, max_gen_len
  • Amazon Titan: inputText, textGenerationConfig

Swap models and you rewrite the body. Powerful, but fiddly.

Converse / ConverseStream
📚 One standard form

A single messages list of role + content works across every Bedrock model that supports messages. Shared settings sit in one place:

  • system: the instructions
  • inferenceConfig: maxTokens, temperature, topP
  • additionalModelRequestFields: model-only extras like Claude's top_k

Swap models and the code mostly stays put.

✅ Rule of thumb: new RAG app, multiple models? Start with Converse. Need a model-only feature or exact native control? Drop to InvokeModel.

🧩Prompt templating: the fill-in-the-blank page

A prompt template is fixed text with named blanks. For RAG Q&A, the two blanks that matter most are:

Blank 1{context}
the retrieved chunks from your vector store
+
Blank 2{question}
the user's question, untouched

The grounding line is doing the real work

Notice the instruction "Use ONLY the context below". That is what turns a chatty model into an answer-from-your-documents model. Without it, the model happily fills gaps from its training memory, and you can't tell which parts came from your data.

Also tell it what to do when the answer is missing: "say you don't know." A model that is allowed to shrug is far less likely to invent a policy.

🛠️Copy-paste: template + InvokeModel (Claude)

This is the pattern from the chat answer, cleaned up. Chunks are joined, filled into the template, and sent in the Anthropic Messages body that Bedrock expects.

import json
import boto3

TEMPLATE = """You are a helpful HR assistant. Use ONLY the context below to answer.
If the answer is not in the context, say you don't know.

Context:
{context}

Question: {question}"""

def build_prompt(chunks: list[str], question: str) -> str:
    context = "\n\n".join(chunks)
    return TEMPLATE.format(context=context, question=question)

def invoke(chunks: list[str], question: str) -> str:
    client = boto3.client("bedrock-runtime")
    body = {
        "anthropic_version": "bedrock-2023-05-31",   # required for Claude on Bedrock
        "max_tokens": 512,                            # required by the Messages body
        "temperature": 0.1,
        "messages": [
            {"role": "user", "content": build_prompt(chunks, question)}
        ],
    }
    resp = client.invoke_model(
        modelId="anthropic.claude-3-haiku-20240307-v1:0",
        body=json.dumps(body),
        contentType="application/json",
        accept="application/json",
    )
    return json.loads(resp["body"].read())["content"][0]["text"]

Same job with Converse (any model)

import boto3

client = boto3.client("bedrock-runtime")

def ask(chunks: list[str], question: str, model_id: str) -> str:
    system = [{"text": "You are a helpful HR assistant. Use ONLY the context. "
                       "If the answer is not in the context, say you don't know."}]
    user_turn = [{"role": "user", "content": [{"text": f"Context:\n" + "\n\n".join(chunks)
                                                     + f"\n\nQuestion: {question}"}]}]
    resp = client.converse(
        modelId=model_id,
        system=system,
        messages=user_turn,
        inferenceConfig={"maxTokens": 512, "temperature": 0.1},
    )
    return resp["output"]["message"]["content"][0]["text"]
💡 Notice the Converse version keeps instructions in system and only data in the user turn. That split is a cleaner habit for RAG.

⚠️Gotchas that show up on the exam and in prod

  • 📦 Too much context. Stuff 40 chunks in and you can blow past the model's input limit. The call fails with a ValidationException. Cap the number of chunks and trim by token count.
  • ✂️ The system prompt gets cut off. If the formatter keeps the user's text and drops the instructions when trimming, the grounding rule vanishes. Trim retrieved chunks, never the instructions.
  • 🧱 Wrong body for the model. Sending a Titan body to a Claude model id is a classic runtime error. Match body to model, or use Converse.
  • 🧷 Missing anthropic_version. For Claude on InvokeModel, leave it out and the body is rejected. Use bedrock-2023-05-31.
  • 🧪 Want JSON back? Ask for JSON in the template, and optionally pre-fill the assistant turn with { so the model starts mid-object. For strict schemas, use tool use with a JSON schema.
  • 🗂️ Version your prompts. A template change is a behavior change. Keep templates versioned, for example in Bedrock Prompt Management, so you can roll back.

⭐TL;DR — the actor's page in six lines

  • The backend's job is turn a raw question into a correctly shaped request.
  • InvokeModel = the model's own JSON body (Claude, Llama, Titan each differ). Converse = one standard shape across models.
  • RAG templates have two key blanks: {context} from retrieval and {question} from the user.
  • Always include a grounding instruction: use only the context, and say "I don't know" when it's missing.
  • Watch the context budget. Too many chunks means a ValidationException, and trimming must never delete the instructions.
  • Keep templates versioned and parameters like temperature in config, not hardcoded.
