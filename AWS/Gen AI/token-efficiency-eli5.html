01 / THE BASICS First, tokens

A token is a word-chunk. Tokens are the unit you're billed in.

The model doesn't read letters or whole words — it reads tokens, which are little chunks of text (roughly ¾ of a word in English). "Hamburger" might be 2 tokens; "cat" is 1.

You pay per token, and — this is the part people miss — you pay in both directions:

Tokens you send → input

Cheaper per token

Your system prompt, retrieved documents, history, and the question. This is where prompt caching helps.

Tokens the model writes → output

Pricier per token

The answer itself. Usually around 3–5× the input rate, so a chatty model can cost more than a fat prompt.

🧸 Kid version: every time you talk to the model, the meter starts running — and it charges for what you say and what it says back.
02 / THE WASTE Why it adds up so fast

In a chatbot, you resend the same huge prefix on every single turn.

Models are stateless. They don't remember your last call — so you send everything again each time: the system prompt, the tool definitions, the retrieved document, the whole running conversation.

On a RAG app, that prefix is most of the payload. And the user only changed one line of it — their new question.

Ask the same document 20 questions, and without caching, you pay to have the model read that document 20 times. Same words. Same cost. Every turn.

🔥 That's the waste. The model re-chews a prefix it already understood. Token efficiency is mostly about making it chew once.
03 / THE FIX Prompt caching · see it

Flip the switch. Watch the cost fall, not the tokens.

Prompt caching tells Bedrock: "this chunk of my prompt never changes — keep it warm." Next call, the model reads it from cache instead of recomputing it, and you're billed at the reduced cache-read rate.

04 / THE LEVERS Every dial you can turn

Six ways to run a cheaper meter.

LEVER 01

Cache the repeated prefix

Keep static content at the start of the prompt and dynamic content at the end. That way the stable prefix stays cacheable across calls.

up to ~90% off input
LEVER 02

Cap the answer length

Set a max output length and ask for concise answers. Output tokens are the expensive ones, so a rambling model quietly costs more than a big prompt.

output is the pricey part
LEVER 03

Send fewer, better chunks

Retrieved context is the biggest slice of a RAG prompt. A reranker lets you keep 3–5 great chunks instead of 20 mediocre ones.

shrinks input a lot
LEVER 04

Right-size the model

Not every request needs the biggest model. Route simple prompts to a smaller, cheaper sibling and save the big one for hard asks.

match cost to difficulty
LEVER 05

Trim or summarize the history

A long chat re-sends its whole story every turn. Keep the last few turns and summarize the rest instead of carrying it all.

stops history bloat
LEVER 06

Batch the non-urgent work

Independent, offline jobs (bulk tagging, backfills) can run as a batch at a large discount instead of on-demand. No one's waiting.

big flat discount

🧸 Priority order: cache the prefix first (easy, huge), then trim what you retrieve, then cap the answer. Those three get you most of the way.

05 / ON AWS Where this lives in AWS

Prompt caching in Amazon Bedrock — two flavours.

⚙️ Implicit Prompt Caching

Bedrock and the model automatically try to reuse eligible prompt prefixes. You add no controls — just keep static content first and dynamic content last to raise the odds of an exact prefix match.

It's best-effort: repeating an identical prompt doesn't guarantee a hit, and hit rates vary. Amazon Nova supports it for text prompts.

🎯 Explicit Prompt Caching

You mark the reusable prefix yourself with cache checkpoints. In the Converse API you add a cache point (e.g. cachePoint) or set a longer ttl; in InvokeModel for Claude models you use cache_control.

Rules that matter: the prefix must meet the model's minimum token count per checkpoint (commonly 1,024 tokens, sometimes 512 or 4,096), there's a maximum number of checkpoints (often 4), and the cache has a TTL — typically 5 minutes, with a 1-hour option on some models.

💵 How cached tokens are billed

Tokens read from cache are billed at the model's reduced cache-read rate — that's the saving. Tokens written to cache may be billed higher than the normal input rate, so caching pays off when a prefix is reused, not for one-off prompts.

Read the cache fields in the response (cached_tokens and cache_write_tokens) to confirm what actually hit — never assume.

06 / WATCH OUT The fine print worth knowing

Four things that trip people up.

  • 🔻 Caching is not a guarantee. It's an availability and eligibility thing — a slightly edited prefix or a cold cache means no hit, and you pay normal input rates for that call.
  • 🔺 Cache writes can cost more. If the prefix changes every request, you're paying the write premium for nothing. Cache what's genuinely reused.
  • ⏳ The cache expires. A 5-minute TTL that resets on each hit means a prompt used less often than the TTL won't stay warm — and a longer TTL option exists for slow-moving sessions.
  • 🧮 Effort should match savings. Estimate how many tokens you'd cache and how often they repeat before building anything. Big and repetitive = worth it; small or one-shot = skip it.
07 / THE WHOLE IDEA One breath

If you remember one thing, remember this.

send less → don't re-send it → meter runs slower

Token efficiency isn't about squeezing quality out of your app. It's about never paying twice for the same words — and on AWS, prompt caching in Amazon Bedrock is the lever that does most of it.
