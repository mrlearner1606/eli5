🧠The big idea in one picture

Imagine a library with no shelf labels. A friend asks, "Find me a 2024 HR policy about parental leave." You would have to open every book in the building. Searching everything is slow, and you might grab a 2015 policy by mistake.

Now imagine every book has a sticky label: year, department, who may read it. You first walk to the HR shelf with 2024 on it, and only then look for "parental leave". That's the whole trick.

🧸 In one breath: metadata is the sticky label. Filtering on it means checking the label before you read the page.

🏷️What is metadata for a RAG chunk?

In RAG, your documents get cut into small chunks, and each chunk becomes a vector. A vector says what the text means. Metadata says facts about the chunk that are not in the meaning:

📄 source

Which file or URL did this come from?

📅 date

When was it published or updated? Stale chunks can be excluded.

🌍 region

Which country or product line does it apply to?

🔐 access tags

Which roles or teams may see it? This is the ACL label.

🧸 Good labels are boring facts you already know about a page. A vector can't tell you those.

🧩Design the label rules first (the schema)

A metadata schema is the list of labels, what type each one holds, and which values are allowed. Decide it before you ingest a single file. Changing labels later means re-ingesting data.

✅ Good schema "Clear and boring" Short lowercase keys like region, year, acl. Real types: numbers stay numbers. Fixed values, like EU or US, not free text.
⚠️ Messy schema "Looks fine until it isn't" Region in one file and region in another. Years as text in some files and numbers in others. Ten spellings for the same team.

In Amazon Bedrock Knowledge Bases, each source document can have a companion metadata file in S3 with the same name plus .metadata.json. It looks like this:

// hr-policy-2024.pdf.metadata.json  (sits next to the PDF in S3)
{
  "metadataAttributes": {
    "department": "HR",
    "year": 2024,
    "is_public": false,
    "region": "EU"
  }
}
🧸 Notice year is 2024 with no quotes. It is a number, and it is stored as one.

🚦Filter at query time, before the vector search

At query time, you send the question plus a filter. The filter is a rule like "department equals HR and year equals 2024". The vector search then only ranks the pages that passed. Here is how the order matters:

✅ Pre-filter labels: HR + 2024→ vector search on the few→ top-k answers always k good ones
⚠️ Post-filter vector search on everything→ top-k from all→ drop non-HR may return fewer than k

Modern stores use an efficient filter: they check the label while they search, so you get the right number of results without scanning the whole pile twice. OpenSearch's k-NN engine supports this for Faiss and Lucene engines.

// Bedrock KB retrieval with a metadata filter (sketch)
{
  "retrievalConfiguration": {
    "vectorSearchConfiguration": {
      "numberOfResults": 5,
      "filter": {
        "andAll": [
          { "equals": { "key": "department", "value": "HR" } },
          { "greaterThanOrEquals": { "key": "year", "value": 2024 } }
        ]
      }
    }
  }
}
🧸 Filter first, then rank. Fewer pages to check means faster, more precise answers.

🔐Labels as the bouncer at the door

The same trick guards private data. Give each chunk an access label, and at query time add a filter for the signed-in user's groups. A nurse never gets the chunks labelled hr-confidential, even if the vector match is perfect. Filter on the server, never on the client, because a client can change its own filter.

⚠️Gotchas that bite real builders

  • 🔢 Quoted numbers don't match. If the metadata file says "year": "2024" but your filter sends the integer 2024, the filter can silently match nothing. Keep types identical across files and queries.
  • 📉 Post-filtering can give you fewer than k. Ask for 5 results, filter out 4 of them afterwards, and you get 1. Prefer pre-filtering or an efficient filter.
  • 🧹 Missing labels are not "no match". A chunk with no region label may be dropped by a region filter. Decide a default and enforce it in ingestion.
  • 🧾 Too many labels, too little use. Every label costs ingestion work and storage. Keep the ones you will actually filter on.
  • 🧨 Client-side filters are not security. Access labels must be applied by the retrieval layer, using the caller's verified identity.
  • 🔄 Changing the schema means re-ingesting. Renaming dept to department means updating every metadata file and syncing the knowledge base again.

⭐TL;DR — the labels in five lines

  • Metadata is a sticky label on each chunk: source, date, region, access tags.
  • Design the schema first: consistent key names and real types (numbers stay numbers).
  • In Bedrock Knowledge Bases, put a .metadata.json file next to each document in S3.
  • Filter at query time, before or during the vector search. Avoid post-filtering that can return fewer than k.
  • Apply access filters on the server with the caller's identity, and watch out for quoted numbers.
