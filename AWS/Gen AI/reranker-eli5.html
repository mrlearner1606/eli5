AWS Gen AI · Explained like you're 5

A second opinion that just re-orders the pile — and somehow makes your answers better.

That's the reranker module in AWS. It doesn't find anything new. It looks at what search already found, grades each one against your question, and puts the best really first.

The problem

Your search is fast, but its order is a bit of a guess.

When you ask a question about your data, the computer first does a quick "nearest neighbor" search. It grabs a handful of chunks that look related to your question. This is cheap and fast — and usually in the right ballpark.

But it grades each chunk in isolation: it compares numbers, not meaning. A vague passage that merely uses the same words can outrank the one paragraph that actually answers you.

So you end up with the right pile, in roughly the wrong order. If you hand the model only the top 3, it may read the three least useful chunks.

🔎 Kid version: a friend finds you a box of toys. The right toy is in there — but it's buried under things that just look similar.
The idea

The reranker reads the question with each candidate, then scores them.

Instead of comparing number-lists on their own, a reranker model takes your actual query and each candidate chunk together, in one go. It's a small, focused model trained for exactly this job: judging "how relevant is this passage to this question?"

It then hands back a relevance score for every candidate, and you sort by that score. The pile is the same — only the order changes.

Because it looks at query and passage together, it catches relevance signals a vector-only search can miss: whether the passage really addresses the ask, whether it's the right kind of detail, whether it's just keyword noise.

How it works

The whole flow, start to finish.

01

Ask in a wide net

Your retrieval step grabs more candidates than you need — say 20 or 50 chunks — using fast vector search. Quantity is fine here; this stage is cheap.

02

Hand the query + candidates to the reranker

You send the user query and the list of chunks to the rerank model. It reads each chunk against the query and returns a relevance score for each.

03

Sort, then keep only the top few

Reorder by the new scores and keep the best 3–5. Now you can pass fewer, better chunks into the generation prompt.

04

The model answers from better context

Mostly-relevant context means more accurate answers, less hallucination, and — because the payload is smaller — lower cost and latency.

Why two stages at all?

Fast-and-rough, then slow-and-careful.

You could run the reranker against every document you own. But that would be slow and expensive — the reranker is a careful reader, not a bulk sorter.

So the two stages split the work by what each is good at:

Stage 1 · Retrieve

Vector search: the wide net

Blazing fast, handles millions of chunks, compares meaning by distance. Great at narrowing. Rough on exact ordering.

Stage 2 · Rerank

The reranker: the careful judge

Slower and more precise, but only runs on the shortlist. Great at ordering. This is where relevance actually gets decided.

On AWS

Where the reranker lives in Amazon Bedrock.

Reranking is a native feature of Amazon Bedrock. There are two ways to use it — one manual, one managed.

⚙️ The Bedrock Rerank API

Call the Rerank operation directly and send it three things: the query, a list of documents, and the model to use. It returns the documents reordered by relevance, each with a score.

Pick how many results you want back (numberOfResults) and which model to score with. This is the manual route if you run your own retrieval pipeline — including outside Bedrock, e.g. OpenSearch.

📚 Amazon Bedrock Knowledge Bases

If you're building RAG with Knowledge Bases, you don't call Rerank yourself. You attach a reranker to the Retrieve or RetrieveAndGenerate call (a reranking configuration), or pick it in the console while querying. The reranker's ordering overrides the default ranking Bedrock would otherwise return.

Reranking works on textual data only, and the Knowledge Base's service role needs permission for it (the bedrock:Rerank action) or the call will fail.

Why it's worth it

Three things you get back.

Better answers

The generation model reads the passages that actually answer the question — so grounded, accurate responses instead of confident noise.

Lower cost

Fewer, more relevant chunks in the prompt means fewer tokens sent to the (much pricier) foundation model on every single call.

Lower latency

A smaller prompt is faster to process. You keep the accuracy without paying to send a huge pile of half-relevant context.

  • Remember: the reranker never retrieves anything new — it only reorders what's already there.
  • Remember: it runs on a shortlist, not your whole corpus — that's what makes it affordable.
  • Remember: it's a Bedrock feature, so you pay per rerank call and no servers to run.
